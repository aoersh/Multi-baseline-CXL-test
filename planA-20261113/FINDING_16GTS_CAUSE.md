# 16 GT/s 成因调查（2026-11-17）

## 结论

**这是一次链路训练降级（link training downgrade），不是 BIOS 配置限制。**

系统要求链路上 Gen5（32 GT/s），硬件也支持，但实际协商到 Gen4（16 GT/s）。
这发生在两台完全相同的设备中的一台上，且整个系统里只有这一条链路如此。

## 证据链

### 1. 硬件能力充足

```
LnkCap: Port #0, Speed 32GT/s, Width x16
LnkCap2: Supported Link Speeds: 2.5-32GT/s, Crosslink- Retimer+ 2Retimers+ DRS-
```

端口硬件支持到 Gen5，插槽也支持 x16（实际协商 x8）。

### 2. 系统明确要求 Gen5，但没达成

```
LnkCtl2: Target Link Speed: 32GT/s, EnterCompliance- SpeedDis-
```

`Target Link Speed = 32 GT/s` 表示软件设定的目标是 Gen5。
若为 BIOS 或平台策略限制，这个字段会显示 16 GT/s。

实际协商结果：

| BDF | 角色 | current | own max |
|---|---|---|---|
| 0000:32:02.0 | mem0 上游端口 | **16.0 GT/s** | 32.0 GT/s |
| 0000:33:00.0 | mem0 端点 | **16.0 GT/s** | 32.0 GT/s |
| 0000:b3:02.0 | mem1 上游端口 | 32.0 GT/s | 32.0 GT/s |
| 0000:b4:00.0 | mem1 端点 | 32.0 GT/s | 32.0 GT/s |

端口与端点同时是 16 GT/s，说明降级发生在整条链路，不是单端问题。

### 3. 全机扫描：只有这一条链路低于自身能力

排除空闲降速（2.5 GT/s）和已到自身上限的设备后，全机**唯一的异常项**：

```
BDF            设备       cur              own max          判定
0000:33:00.0   CXL [0502] 16.0 GT/s PCIe   32.0 GT/s PCIe   低于自身能力
```

其余 PCIe 设备（RAID 卡 16 GT/s、网卡 5 GT/s、GPU 2.5 GT/s 空闲）
都在各自能力范围内。**因此不是 socket0 整体降级，也不是平台级策略。**

### 4. 两台设备除链路外完全一致

| 项目 | mem0 (node2) | mem1 (node3) |
|---|---|---|
| PCI ID | `1b00:c001` rev 01 | `1b00:c001` rev 01 |
| 固件 | `10.40.1.060f.00` | `10.40.1.060f.00` |
| 序列号 | `...0a66` | `...090f` |
| 链路 | **16 GT/s x8** | 32 GT/s x8 |

固件相同、型号相同、序列号相邻，排除了设备固件或型号差异。

### 5. 没有 AER 错误

两个端点和端口的 `aer_dev_correctable`、`aer_dev_nonfatal`、`aer_dev_fatal`
所有计数均为 0。

**这一点很重要**：降级是"干净"的，没有留下任何错误记录。这正是它危险的地方
——监控看不到任何告警，只有实测性能才知道。

### 6. 路径上有 2 个 retimer

```
Retimer+ 2Retimers+
```

Gen5 信号完整性最常见的失守点就是 retimer。两条链路都报告同样的 retimer 拓扑，
但只有一条跑到 Gen5，说明差异可能来自：
- retimer 固件/配置
- 连接器或线缆的物理状态
- 走线差异

**这一步无法从软件侧进一步缩小范围**，需要厂商对这两个插槽的走线说明，
或物理检查。

## 已撤回的一项证据

早先我曾用 `multichase` 的聚合吞吐推算带宽上限，得出"node2 饱和在 14.14 GB/s
≈ Gen4 x8 理论值 15.75 GB/s 的 90%"，并据此论证降级为真。

**这个论证作废。** 后续重复测量得到 5.94 / 6.91 / 7.81 GB/s 三个不同结果，
且曾算出 20.14 GB/s（超过 Gen4 理论上限），说明该带宽换算不可靠。
原因包括：K 条链分批执行、预热遍历导致部分命中 L3、多进程环复用等。

可靠的只有**比值**：node3/node2 在所有测量中稳定为 1.20–1.37，
与延迟比 19.8% 一致。绝对值不可引用。

## 对论文的影响

**主结果不受影响。** 论文主张是"同型号设备的链路速率差异，其代价随负载放大
4.5 倍"，只需要"两条链路速率不同且其余相同"，成因是次要的。

**但这个发现让故事更强了**，因为它把性质从"配置差异"变成"静默降级"：

> 一块发货支持 Gen5 的 CXL 设备，实际只协商到 Gen4，且不产生任何 AER 错误。
> 系统目标速率是 32 GT/s，实际 16 GT/s。监控看不到异常。
> 代价在空载时只有 18.5%，在负载下扩大到 82.9%。
> 也就是说，一次静默的链路降级，会在生产负载下造成接近一倍的尾延迟劣化。

这个框架比"我们比较了两种配置"有价值得多，也更贴近运维现实。

## 仍需确认

1. 两个插槽的走线/retimer 是否相同（需厂商或主板手册）
2. 重新插拔或换插槽后是否恢复 Gen5（需停机，且会改变现有数据）
3. BIOS 中是否有该插槽的 PCIe 速率设置覆盖（`Target Link Speed=32GT/s`
   已暗示没有，但值得确认）

这三项都需要你或管理员介入，且第 2 项会破坏当前实验数据，建议在论文定稿后再做。
